# Physics extensions: powertrain, brakes, aero, hybrid, setup, ODE core and surfaces (hooked code)

CSP 0.3.0-preview649 (build 4184) wraps or re-implements 37 hooked functions of `ksPhysicsAC.lib`, `ksPhysicsCoreODE.lib`, `SurfacesManager.obj` and `DynamicTrackManager.obj` that belong to the drivetrain, engine, turbo, brakes, ABS, traction control, DRS, wings, setup, lap rules, surface table and the physics core, and it calls 25 more functions of the same classes as lookups. This file maps every one of those 62 table rows (group `physics_powertrain_aero` of `hook_groups.tsv`), the CSP-own functions they call that are not table rows (the cphys loaders, the air-density law, the Embree ray caster), and answers the five questions of the task. It builds on `physics_car_hooks.md` (tick, per-car extension object `ext`, switches) and `physics_documented.md` (keys, Lua API) and does not repeat them; cross references are by section name.

Conventions: dwrite.dll addresses are RVAs (image base `0x180000000`), acs.exe addresses are `0x14...` VAs as in `docs/map`. Hook categories as in `physics_car_hooks.md` 2: **A** pass-through / event, **B** wraps the original, **C** replaces it (original not called, or only under a condition), **D** lookup (CSP calls acs.exe through the slot). "slot" = RVA of the data cell that holds the trampoline to the original. `ext` = the per-car extended object (`physics_car_hooks.md` 2a); `ext+0xNNN` offsets below are observed in these hooks, names are [interp]. Evidence markers: `[dll]` decompile / table, `[dll-bytes]` instructions read by hand, `[log-csp]`, `[ini]`, `[sdk]`, `[prior]`, `[interp]`.

## 1. What it does

### 1.1 In one page

1. **Another physics core underneath everything.** `ksPhysicsCoreODEFactory::create` (the only place acs.exe builds its `IPhysicsCore`) is fully replaced and returns CSP's `cphys::ode64_core` (0x32c0 bytes, double precision ODE with libccd, multi-threaded collisions). Car code keeps calling the abstract interfaces, so bodies, joints, rays and meshes are answered by CSP's objects. Tyre rays go to Intel Embree (closest hit) instead of ODE's ray-vs-trimesh. `[dll]` 2.6.
2. **Air density has an altitude law, for every car.** Three replaced functions (`Car::updateAirPressure`, `PhysicsEngine::getAirDensity`, and a thread-local override written in the `Engine::step` hook) plus the CSP function at `0xaf7760` compute dry air from the standard barometric formula with a near-ground temperature blend. Humidity and weather pressure are **not** inputs. 1.2.
3. **The drivetrain, engine and turbo hooks are wrappers with fall-through.** Each looks up `ext` by `Car+0x3e9c`; if the sub-object it needs (`ext+0x1e0` diff model, `ext+0x1e8` clutch model, `ext+0x200` engine object, per-turbo table `ext+0x108`) is absent it calls the original. The CSP re-implementations of `step2WD` and `step4WD` run for the **first physics car only** (`Car+0x3e9c == 0`) and are a full second copy of acs's stepping code. 2.1.
4. **Brakes, ABS and traction control are replaced only when the car's data carries the CSP section** (`brakes.ini [_EXTENSION] ENABLE`, the CSP ABS controller section, `electronics.ini [TRACTION_CONTROL_2]`). Without it they are the original plus small always-on changes: `ABS::isInAction` is redefined for every car, brake temperatures keep running when the AI drives the player's car, brake temperature retention rule. 2.2.
5. **Wings:** two new per-wing keys (`FIXED_AOA`, `DOWNWARD_NORMAL`), CSP's own ground-height function, aero maps and fans as a wrapper around `AeroMap::step`. 2.3.
6. **Setup:** `SetupManager` gets a per-car table of extra (script / controller-driven) items, its own `step`, and a second pass over the setup file after the stock `load`. 2.4.
7. **Track surfaces:** `SurfacesManager` is extended with "surface tweaks" read from the same `surfaces.ini` (extended type from the sound file name), and `getSurface` gets a longest-prefix fallback for mis-named meshes ("Suspicious surface mismatch: ... doesn't seem like a wall!" [log-csp]). `DynamicTrackManager` is a graphics-only class (grooves, puddle texture). 2.5.

### 1.2 The five questions

**(1) How air density gets its altitude law.** Hooks: `Car::updateAirPressure` (acs 0x140276ae0, RVA 0x596f80, C), `PhysicsEngine::getAirDensity` (acs 0x140263a60, RVA 0x68ab90, C) and the `Engine::step` hook (acs 0x1402880e0, RVA 0x5cbdc0). All three call CSP functions that are not table rows:

| Function (RVA, size) | Role |
|---|---|
| 0xaf7760 (379 B) | air density in kg/m3: `rho = 3.4836106 * P / T_K` |
| 0xaf75f0 (358 B) | the same chain returning the pressure P in kPa (also used by the `Tyre::step` hook at call site 0x6b11b2 and by 0x41f0f0 / 0x4ebc50) |
| 0xaf7010 (about 1.5 kB, entry 129 B) | "local temperature" `Tc = Z(roadTemp, airTemp, |PhysicsEngine+0x164|, groundHeight)` |
| 0x68aac0 (193 B) | per-car provider: `rho_law(...) * perCarMultiplier[physicsGUID]`, or constant 1.1839 when ext flag byte `+0x6cf` is set, or the stock `1.2922 - 0.0041 T` when the car has no avatar object |
| 0x1126df0 (1,736 B) | writes the base altitude globals `0x268c430` (used with flag 1) and `0x268c48c` (flag 0) |

Formula in words `[dll-bytes]`: height `h = baseAltitude + car position Y` (0 when the base is NaN); `T_K = Tc + 273.15`; `x = max(1 - 0.0065 h / T_K, 0)`; `P = max(101.325 * x^5.2557769, 1.19e-7)` kPa; `rho = 3.4836106 * P / T_K` (3.4836 = 1/0.287058, dry air). Inputs: `h` (track altitude, car Y); `PhysicsEngine+0x100` ambient temperature, `+0x104` road temperature, `+0x164` (a value taken as absolute value; [interp] wind speed, the `Wind` object of `docs/map/aero.md` 2 is 0x14 bytes ending there); the ground height of the point from the CSP `RaceEngineer::getPointGroundHeight` hook (0x10ebeb0; 0.5 m default). Humidity and the WeatherFX pressure are **not read** anywhere in these three functions.

Where the base altitude comes from: `0x11274c0` (479 B) parses the track's `data/surfaces.ini` with CSP's own INI parser and calls `0x1126df0`, which looks for `[_EXTENSION] PIT_ALTITUDE`, then `[ALTITUDE] BASE`; if neither is present it calls the table function `0x11d0ab0` (1,213 B), a **hard-coded list of about 30 Kunos track ids to pit altitude in metres** (read: ks_barcelona 118, ks_black_cat_county 1250, ks_brands_hatch 130, drift 100 together with ks_drag, ks_highlands 240, imola 37, ks_laguna_seca 230, magione 235, mugello 259, monza 182, ks_nordschleife 625, touristenfahrten 574, ks_nurburgring 619, ks_red_bull_ring 678, ks_silverstone 153, spa 418, trento-bondone 380, ks_vallelunga 195, ks_zandvoort 5, india 193, grandsambuc 583, forliring 28, greatwall 440, korea 2, la_canyons 1341, auto24ring 4, monaco_1966 3; the pairing of names to values inside shared branches is approximate [interp]; spa 418 and the log line "Pit altitude for current track: 418" agree [log-csp]). It then subtracts the Y of the node `AC_PIT_0` ("Pit Y coordinate: 22.9886") to get the altitude of world Y = 0 (395.011 m for Spa, equal to [prior] 5.1). A track without any source gets NaN, i.e. altitude 0. For `monaco_2017` the log says altitude 8: no `monaco_2017` literal was found in the table, so another branch or fallback (function 0x11cf7e0, not read) supplies it [open].

Comparison with `prior/csp_survey.md` 5.1: the earlier fit `rho = 1.167658 * exp(-posY/8415)` and its "humidity about 0.66" guess are replaced by this law. Worked check with the numbers of [prior] 5.1: Spa pit (Y = 5.326 so h = 400.34 m), Tc = 15.2 C (air 14.0 C, road 20 C: +1.2 K from Z): `T_K = 288.35`, `x = 0.99098`, `P = 96.61 kPa`, `rho = 1.1671`, recorded 1.16714. The 1.2 K offset is `Z`'s blend and is the only thing that made the humidity story look necessary. At sea level and 15 C the law gives 1.2250 against 1.2307 stock, so CSP is lower than stock even without altitude. The stock engine multiplier `0.8263` is applied on top (docs/map/aero.md 5.2 and drivetrain.md 5.5): the engine sees the same density through the thread-local, per-car value.

Slipstream (same hook): `rho' = rho * ((0.75/g - 1) * clamp(s*g*SLIPSTREAM_MULT) + 1)` where `g = Car+0x3e24 * SLIPSTREAM_GAIN_MULT` and `s` the strongest wake of the other cars (`SlipStream::getSlipEffect` lookup). With the rules block at defaults this equals the stock `(rho - m rho)(0.75/g) + m rho` form; the smoothed copy (factor 0.015 per step) is written to `Car+0xaec`.

**(2) ODE replacement and the ray cast.** See 2.6. Short form: `ksPhysicsCoreODEFactory::create` (RVA 0x6216c0) allocates a 0x32c0-byte CSP object whose constructor `0x927870` (682 B) creates its own ODE world (`0x15f6ca0`) in **double precision**, prints "ODE flags: ... ODE_EXT_libccd ... ODE_double_precision" and sets the constants `gravity -9.806 (exact double; stock float -9.80599976)`, `ERP 0.3`, `CFM 1e-7`, `contact max correcting velocity 3.0` (same as stock), `contact surface layer 0.001 m` (stock `dWorldSetContactSurfaceLayer(0)`, `docs/map/physics_engine.md` 3.1), quick-step iterations 48 (unused). acs.exe's Car / Suspension / Tyre / Wing code is untouched because it only sees `IPhysicsCore`, `IRigidBody`, `IJoint`, `ICollisionObject`, `IRayCaster`. There is **no hook on `Track::rayCast`, `RayCaster::rayCast` or `PhysicsCore::rayCast`**; the ray cast is replaced by object substitution: `createRayCaster` (core vtable +0x88, RVA 0x9393d0) returns a CSP `ode_impl_raycaster` whose `rayCast` (RVA 0x9350a0, 96 B) sends a straight-down ray (`dir.y == -1.0`) to a track-supplied native module when one registered (`CUSTOM_RAYCASTER`, `csp_Raycast_v1`, function pointer `0x26a9668`), otherwise to `0x93be50` (731 B): Embree closest hit on the BVH built by `0x92d620` (963 B, "Starting Intel Embree build", device with `threads=1`), with an ODE ray fallback when Embree is switched off or not ready (`ODE_BATCH_RAYCAST`, flag bytes `0x269507f`, `0x26a4cfe`).

**(4) Setup.** CSP adds script-owned setup items (`[CUSTOM_SCRIPT_ITEM_n]` with `ID` and a mandatory `DEFAULT`), controller-driven items (`EXT_CONTROLLER`), conditional visibility (`EXT_ENABLED_WITH`, `EXT_VISIBLE_WITH`), named value lists and unit display (`LABEL_n`, `VALUE_n`, `DISPLAY_VALUE_IN_BRACKETS`, `DISPLAY_MULTIPLIER`, `UNITS`: parser `0x1134910`, 8,172 B, strings at 0x228c2b8..0x228c368) and items that move suspension geometry (`<joint>_LENGTH_OFFSET_<wheel>`, `_POS_A_SETTING_`, `_POS_B_SETTING_`, `_POS_SETTING_`: parser `0x89c570`, suspension brief). The setup **file** is hooked in `SetupManager::load` (0x10f5510: second pass over the same file) and the manager in `SetupManager::init` (0x10f4e00) and `SetupManager::step` (0x10f4f10). The UI classes (`SetupScreen`, `SetupTab`, ...) are in another group. Details in 2.4.

**(5) What applies to a stock Kunos car with extended physics off.** Table in 5. In short: the ode64 core, the air-density law, `ABS::isInAction`, the surface table, `BrakeSystem` temperature handling and the always-called wrappers apply; COSMIC, advanced brakes, ABS PID, TC2, ERS, engine and pedal maps, aero maps, controller-driven setup items and everything driven by `data/script.lua` need the car's own data. **Two things are not settled by static reading and matter for a port**: whether `ext` exists for a stock car (log and density data say yes, the static call chain says it should not, see 5 and 8) and whether CSP's own `step2WD` / `Engine::step` post-processing is numerically identical to acs's for stock data (8).

## 5. How it is switched on

Switch chain for the per-car object, as far as it is read: `INIReader::getInt` hook (0x5f0650) sees `[HEADER] VERSION` of the car being loaded; if the value starts with `extended-` or `extendedV2-`, or the global byte `0x26998bd` is set, it calls `0x5f0170`, which allocates `ext` and fills it through `0x7f6150` -> `0x7f6d10`. The global is set by `general.ini [PHYSICS_EXPERIMENTS] EXTENDED_PHYSICS` (`0x138ded0`), by the session loader with run-time-decoded keys (`0x56b6d0`), by the new-mode manifest `FORCE_EXTENDED_PHYSICS` (`0xd2fce0`) and by `0x5f0170` itself after the first car (index 0) is extended (when `0x26a2c30` is 0). Everything inside the loaders is then gated per sub-object by the car's data (table in 2.7).

| Behaviour | Needs `ext` | Needs the sub-object | Stock Kunos car, extended physics off |
|---|---|---|---|
| ode64 core, Embree rays, gravity / surface-layer constants | no | no | **applies** `[dll]` |
| `ABS::isInAction` redefinition | no | no | **applies** (speed > 1 m/s and absOverride < 0.9) |
| `BrakeSystem::stepTemps` also for the AI-driven player car | no | no | **applies** (player car 0 under AI / autopilot; relevant to AI-lap recordings) |
| `BrakeSystem::reset` retain rule | no | server rule | online only |
| `SurfacesManager` tweaks, `getSurface` prefix fallback | no | no | **applies** (log "Suspicious surface mismatch ... 02OFFTRACK-PIT") |
| `Drivetrain::getCurrentGear` empty name, `Engine::getSafeTurboLevel` clamp, `isGearboxLocked` flag 0x400, `DRSManager` flags | no | no | applies, no value change for stock data |
| `Engine::loadINI` throttle-curve cancel | no | `SKIP_THROTTLE_CURVES=1` | off by default |
| Air density altitude law, slipstream with rules block, engine density | yes (`ext+0x228`) | no | **applies** in practice: measured on the F2004 (`VERSION=1`) at Spa [prior][data] and the log of `rss_formula_hybrid_2020` (`VERSION: 2`) shows the cphys loaders running ("Cphys Drivetrain Initialized.", "CPHYS ERS not enabled") even though neither car is `extended-`; **the static path that creates `ext` for them is not found** (8) |

## 7. Port difficulty for rustyAC

**Rating: L overall; the always-on part (air law, `isInAction`, brake temps, surface prefix rule) is S; matching CSP's own drivetrain / engine copies is M and unproven; double-precision ODE + Embree is XL and out of scope.**

What exists in the port to reuse: `crates/rustyac-physics` has the drivetrain, engine, turbo, brakes, ABS, TC, wings, setup items and the stock surface/ray path with oracles against acs.exe (`docs/port/drivetrain.md`, `contacts.md`, `tracks.md`, `awd_ers.md`; `chassis_compare`, `car_oracle`, `tyre_oracle`). The CSP additions that a "CSP mode" would need, ordered by value and cost:

|---|---|---|
| Air density law (`0xaf7760`) with `Z` temperature blend and per-track pit altitude table | S | one function in the aero/engine path; prove against `f2004_spa_ai.csv` (five points of `physics_documented.md` 2.4(b), 1.16714 at the pit) and against a second track using the table value; `Z` itself must be read (decompile request 0xaf7010) |

| CSP ground height (`n . p - d` plane from contact points) instead of the vertical-ray plane distance | S | affects ground effect only through the wing `LUT_GH_*`; differs by `1/n.y` |

| Embree closest-hit | L | the oracle's ODE first-hit differs only on overlapping surfaces; a mesh-ray closest hit in `rustyac-physics` track code is enough, no Embree needed |
| Whole cphys layer (COSMIC, brakes, ABS PID, TC2, ERS, maps, script host) | XL | out of scope; stock data paths are not affected |

What could be proven and how: (a) air density per row of the recording (it is a pure function of Y, T, road T and pit altitude); (b) `step2WD` numerics: run the existing drivetrain oracle (acs original) against a recording that was made with CSP present and compare rpm / wheel speed over a launch and a shift; if the two disagree, the CSP copy differs; (c) engine torque: `Engine+0x130` post-processing multipliers should be 1.0 for stock data, check outTorque against the stock formula in a steady state; (d) `isInAction` against the shared-memory `abs` field.
